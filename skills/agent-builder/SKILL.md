# Agent 架构构建指南 (Agent Builder Skill)

你现在拥有设计与构建全领域 AI Agent（包括代码助手、客服机器人、自动化运维、研究分析、业务流编排等）的资深架构能力。

---

## 一、 核心架构哲学 (Core Philosophy)

> **“模型本身就已经懂得如何成为一名 Agent，宿主程序的核心任务是搭建舞台，并退到一旁。”**

一个实用的智能体架构并不是复杂的工程堆砌，而是一个极简的行动循环（Agent Loop）：

```text
LOOP (自主行动循环):
  1. 模型观察：当前上下文历史 (Messages) + 可用工具清单 (Tools)
  2. 模型决策：继续行动 (调用工具) 还是 结束并回答 (输出文本)
  3. 若行动：宿主执行对应工具 ➔ 将结果回填 Messages ➔ 继续进入下一轮循环
  4. 若回答：将最终结论呈现给用户 ➔ 等待下一次用户输入
```

**魔法在于大模型本身的推理能力，而不是繁复的代码。宿主外壳（Harness）只负责提供机会与安全边界。**

## 二、 构成 Agent 的三大支柱 (The Three Elements)

### 1. Capabilities（行动力：它能“做什么”？）
Agent 能够调用的原子工具：命令行执行、读文件、写文件、改代码、调接口。
- **设计准则**：起步时仅提供 **3~5 个最核心的原子能力**。只有当 Agent 因为缺失某项能力而导致任务反复失败时，再考虑增添新工具。

### 2. Knowledge（专业知识：它“知道什么”？）
领域规则、代码规范、业务流程、提示词指导。
- **设计准则**：专业知识应当**按需动态加载（On-demand）**，绝不要在启动时一股脑全塞进 System Prompt。

### 3. Context（上下文线索：它“经历了什么”？）
对话历史消息列表 —— 它是将一系列离散工具调用串联成连贯业务行为的记忆纽带。
- **设计准则**：上下文空间是极为珍贵的资源。隔离高噪音子任务（Subagent）、截断超大工具输出、及时进行上下文压缩淘汰（Compaction）。

## 三、 智能体复杂度演进阶梯 (Progressive Complexity)

从极简起步，只在实际运行遭遇瓶颈时才升级复杂度：

| 阶段 | 增加的核心机制 | 触发升级的瓶颈痛点 |
|---|---|---|
| **Level 1: 基础循环** | 3~5 个基础工具 + While True 循环 | 起步标配，赋予基础行动力 |
| **Level 2: 任务规划** | 任务看板（如 todo_write） | 多步骤任务容易迷航或丢三落四 |
| **Level 3: 子代理隔离** | 派生全新上下文的子循环 (Subagent) | 大量排查探路日志撑爆主上下文 |
| **Level 4: 动态技能** | 两层提示词与按需加载 (load_skill) | 多领域专业规约导致 System Prompt 臃肿 |
| **Level 5: 上下文压缩** | 自动淘汰旧轮次并沉淀核心摘要 | 超长任务逼近 LLM 窗口极限 |

> **提示：业界 80% 以上的实用 Agent，只需做到 Level 2~3 就足以解决绝大多数工程问题。**

## 四、 常见反模式清单 (Anti-Patterns)

| 反模式 | 潜在问题 | 正确做法 |
|---|---|---|
| **过度工程化** | 在需求明确前设计极度繁琐的框架 | 先用纯 Python 写几十行基础循环 |
| **工具功能臃肿** | 工具数量泛滥，导致模型产生选择困难症 | 起步 3~5 个，保持单一职责 |
| **死板工作流 (DAG)** | 试图用硬编码条件分支规定死模型的每一步 | 信任模型决策，让模型根据工具反馈自主推导 |
| **前端全量灌知识** | 一启动就把几万字规范全塞入系统提示词 | 采用两层架构，按需调用 load_skill |
| **微操控制狂** | 处处限制模型思考细节 | 只管住安全边界（权限拦截），放手让模型推理 |

## 五、 Agent 设计思维转变

- **从**：“我怎么写死代码让系统去完成 X？”
- **转变为**：“我需要给大模型提供什么能力和工具，让它自主推导完成 X？”

最优秀的 Agent Harness 运行时外壳往往非常纯粹：**极简的循环、纯粹的工具、干净的上下文。把推理交给模型，把安全交给外壳。**
